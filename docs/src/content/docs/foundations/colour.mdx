Name the role, not the colour. Every value comes from a warm neutral ramp and an orange accent ramp, computed in OKLCH so equal steps look equal.

The contrast shown is computed from the tokens at build time. WCAG 2.2 AA asks for 4.5:1 on text and 3:1 on graphics and control edges.

## OKLCH

Think of a colour picker with three sliders: light to dark (L), grey to vivid (C) and which colour (H). Darkening a pale colour by adding black is like black paint: it gets darker but also duller, so a green turns grey-olive. Here a colour family is one hue and one peak vividness, and its steps come from moving the lightness slider alone, so a pale teal and a deep teal are plainly the same teal.

Since 0.10.0 every colour token is written that way in the CSS, as `oklch()`: `--c-item-live: oklch(0.48 0.0816 200.45)`. It's normal CSS. Each value is gamut-clipped to sRGB, so it shows the same on every screen, and the build reads each one back and checks it is exactly the colour it asserted contrast for. OKLCH gives even steps but doesn't promise contrast, which is why every pairing is still checked.

Mixing a tint (a chip's background from its colour, say) uses `color-mix(in oklab, …)`: the same space without the hue angle, so a mix towards a grey doesn't swing through other hues on the way.

## Browser parts

The tokens' stylesheet also colours what the browser draws itself, so it follows the theme. The text caret and any native checkbox, radio, slider or progress bar take `text-accent`. The bright accent isn't used here: beside it, Chrome draws a native control's track dark in light mode. Scrollbars take `border-strong` on a clear track; their width stays the browser's. Nothing to import: it comes with the tokens.
